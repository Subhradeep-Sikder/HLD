## 🎯 Overview: How an HLD Interview Begins

* **Core Rule:** Every real-world HLD interview starts with **System Measurement & Estimation** (Back-of-the-Envelope Calculations).
* **The Hotstar Analogy:** The only core difference between a tiny website built on your laptop and Hotstar.com is **scale**. Scale requires proper engineering.
* **Why Estimate First:** If an interviewer asks to design WhatsApp, jumping straight to drawing architecture boxes (servers, DBs) is a red flag. You must first ask how many users exist and calculate what servers are required.

## 📊 Core System Criteria (Metrics to Ask the Interviewer)

### 1. Latency
Time taken by the system to return a response to a single user action.

| Latency Range | System Status | Human Perception |
| :--- | :--- | :--- |
| **$< 100\text{ ms}$** | 🟢 **Top-tier / Very Good** | Indistinguishable to the human mind. |
| **$100\text{ ms} - 300\text{ ms}$** | 🟡 **Almost Very Good** | Practically imperceptible. |
| **$1\text{ Sec}$** | 🟠 **Noticeable / Sub-optimal** | Humans clearly notice the delay. |
| **$> 1\text{ Sec}$** | 🔴 **Bad** | Ruined UX, users abandon the platform. |

---

### 2. Throughput
* Total number of requests the system handles in **1 second** (Requests Per Second / RPS).
* *Example:* If WhatsApp has 50 Crore users and 2 Crore are active in any 1 second, the required throughput is at least **2 Crore RPS**.

---

### 3. Bandwidth
* **Definition:** Total size of data flowing through the system in 1 second, measured in **Bits Per Second (bps)**.
* **Throughput vs. Bandwidth:**
  * **Throughput:** Counts *number of requests* per second.
  * **Bandwidth:** Counts *total data volume* of those requests per second.
* **Formula:**
  $$\text{Bandwidth} = \text{Throughput (Requests/sec)} \times \text{Average Request Size}$$

---

### 4. Normal vs. Peak Traffic
* **Concept:** System usage is never uniform across the day. Hotstar has low traffic on regular days, but massive spikes during India vs. Pakistan matches.
* **Rule of Thumb:** Design systems for **Peak Traffic** (otherwise it crashes like IRCTC at 10 AM Tatkal time).
* **Assumption:** If the interviewer doesn't specify, assume:
  $$\text{Peak Traffic} = 3\times \text{ Normal Traffic} \quad \text{(or } 5\times \text{ / } 10\times \text{ if specified)}$$

---

### 5. Read-Heavy vs. Write-Heavy Applications

| Category | Description | Real-World Examples |
| :--- | :--- | :--- |
| 📖 **Read-Heavy** | Users fetch/view data far more than uploading it. | **YouTube, Instagram** *(10 creators vs. 90 viewers consuming content)* |
| ⚖️ **Balanced** | Equal flow of incoming and outgoing data (full-duplex). | **WhatsApp** *(both parties reading and writing messages)* |
| ✍️ **Write-Heavy** | Frequent continuous data pushes to the system. | **Uber** *(drivers pushing location every 5 seconds)*, **Zomato** order tracking |

---

### 6. Percentiles (P95 / P99) vs. Average Latency

#### Why Average Latency is Misleading:
* Suppose 90 users experience **$50\text{ ms}$** latency and 10 users experience **$2000\text{ ms}$** ($2\text{ sec}$).
* **Average Calculation:**
  $$\text{Average Latency} = \frac{(90 \times 50) + (10 \times 2000)}{100} = \frac{4,500 + 20,000}{100} = \mathbf{245\text{ ms}}$$
* **The Hidden Problem:** $245\text{ ms}$ looks "Very Good" on paper, hiding the fact that **$1 \text{ in } 10 \text{ users}$ ($10\%$ of total traffic) experiences a terrible 2-second delay**.

#### Percentiles:
* Sort all latencies from fastest to slowest.
  * **P95:** The latency value at the 95th percentile (in this case $= 2000\text{ ms}$).
  * **P99:** The latency value at the 99th percentile (in this case $= 2000\text{ ms}$).
* **Key Takeaway:** Companies rely on **P95/P99** to fix tail latencies because average metrics hide severe issues for millions of users.

## ⏱️ Standard Latency Numbers (Every Engineer Must Know)

| Storage / Operation | Typical Latency | Exact Scale | Comparison Context |
| :--- | :--- | :--- | :--- |
| 🪑 **RAM Read** | **$100\text{ ns}$** (nanoseconds) | $10^{-9}\text{ sec}$ | Ultra-fast baseline |
| ⚡ **SSD Read** | **$100\ \mu\text{s}$** (microseconds) | $10^{-6}\text{ sec}$ | $\sim 1,000\times$ slower than RAM |
| 💾 **HDD Read** | **$10\text{ ms}$** (milliseconds) | $10^{-3}\text{ sec}$ | $\mathbf{100,000\times}$ slower than RAM |
| 🏙️ **Network: Bengaluru to Mumbai** | **$20\text{ ms}$** | Local route | Low regional latency |
| 🌍 **Network: Bengaluru to USA** | **$200\text{ ms}$** | Cross-continent | $10\times$ slower (Physical distance limit) |

> **Key Takeaway:** Reading from HDD is $100,000\times$ slower than RAM. Physical distance cannot be beaten by coding—hence the need for **CDNs** (placing USA servers in Mumbai) and **Caching** (RAM).

## 🧮 Step-by-Step Back-of-the-Envelope Calculation: Designing WhatsApp

### Lecturer's Assumptions
* **Daily Active Users (DAU):** $50\text{ Crore}$ ($50 \times 10^7$).
* **Messages per user per day:** $40\text{ messages/day}$.
* **Message breakdown:** $90\%\text{ Text}$ and $10\%\text{ Photos}$.
* **Size assumptions:**
  * $\text{Text} = 200\text{ Bytes}$
  * $\text{Photo} = 200\text{ KB}$ ($200 \times 10^3\text{ Bytes}$)
* **Seconds in a day:** $86,400\text{ seconds}$ *(rounded to $100,000$ for quick calculation)*.

---

### Step 1: Throughput Calculation (Requests Per Second)

$$\text{Total Requests per Day} = 50 \times 10^7 \text{ users} \times 40 \text{ requests} = 2000 \times 10^7 \text{ requests/day}$$

$$\text{Throughput (RPS)} = \frac{2000 \times 10^7}{86,400} \approx \frac{2000 \times 10^7}{100,000} = \mathbf{200,000\text{ RPS (2 Lakh RPS)}}$$

---

### Step 2: Server Count Estimation

* Assume $1\text{ AWS Server}$ handles **$1,000\text{ RPS}$ maximum**.

$$\text{Servers Required} = \frac{200,000\text{ RPS}}{1,000\text{ RPS/server}} = \mathbf{200\text{ Servers}}$$

---

### Step 3: Bandwidth Calculation

* **Message breakdown for 1 user ($40\text{ messages total}$):**
  * $36\text{ Text messages} = 36 \times 200\text{ Bytes} = \mathbf{7,200\text{ Bytes}}$
  * $4\text{ Photo messages} = 4 \times 200 \times 10^3\text{ Bytes} = \mathbf{800,000\text{ Bytes}}$
  * **Total data per user/day:** $7,200 + 800,000 = \mathbf{807,200\text{ Bytes}}$

$$\text{Total Daily Data} = 807,200\text{ Bytes} \times 50 \times 10^7 \text{ users}$$

$$\text{Bandwidth (Bytes/sec)} = \frac{\text{Total Daily Data}}{86,400}$$

$$\text{Bandwidth (Bits/sec)} = \text{Bandwidth (Bytes/sec)} \times 8$$

## 💡 Must Remember for Interview (From Video)

1. **Start with math:** Always start an HLD interview with Back-of-the-Envelope estimations before sketching components.
2. **Scale defines design:** Scale is the primary distinction between a side-project and production systems like Hotstar.
3. **Avoid extremes:** Bad estimation leads to either **Overspending** (wasting money) or **Under-engineering** (system crash).
4. **Target latency:** Target latencies under $100\text{ ms}$ for top UX; delays above $1\text{ second}$ ruin user retention.
5. **Throughput vs. Bandwidth:** Throughput measures request count/sec; Bandwidth measures total data volume/sec.
6. **Peak capacity:** Always design architecture around **Peak Traffic** (default assumption $= 3\times$ Normal Traffic).
7. **P95/P99 over Average:** Tail latencies must be evaluated using **P95/P99 percentiles**, never average latency.
8. **Memory hierarchy:** RAM read ($\sim 100\text{ ns}$) is dramatically faster than SSD ($\sim 100\ \mu\text{s}$) and HDD ($\sim 10\text{ ms}$).
9. **Physical constraints:** Speed-of-light propagation across long distances enforces hard physical limits *(e.g., Bengaluru to USA RTT $\approx 200\text{ ms}$)*.
10. **State assumptions:** All estimation numbers (DAU, request counts, payload sizes) are assumptions—state them clearly and update immediately if the interviewer suggests different figures.

## 📑 Quick Revision Table

| Concept | One-Line Summary |
| :--- | :--- |
| **Back-of-the-Envelope Estimation** | Rough preliminary math to establish system scale, throughput, storage, and server bounds. |
| **Overspending vs. Under-engineering** | Buying excessive capacity for small scale vs. under-provisioning a high-scale service. |
| **Latency Threshold ($<100\text{ ms}$)** | The gold-standard response time where interactions feel instantaneous. |
| **Throughput (RPS)** | The total number of incoming requests a system processes per second. |
| **Bandwidth (bps)** | Total network payload size transmitted per second ($\text{RPS} \times \text{Avg Payload Size} \times 8$). |
| **Peak Traffic Factor** | Designing capacity for traffic spikes (typically $3\times$ to $10\times$ normal volume). |
| **P95 / P99 Percentiles** | Latency metrics capturing worst-case user experiences hidden by average calculations. |
| **RAM vs. SSD vs. HDD Latency** | Memory hierarchy speeds: RAM ($100\text{ ns}$) $<$ SSD ($100\ \mu\text{s}$) $<$ HDD ($10\text{ ms}$). |

> ### 📝 Interview Tips (Personal Notes, Not from Video)
> * **Calculate out loud:** Perform your estimation math out loud on the whiteboard using round figures *(e.g., rounding 86,400 seconds in a day to 100,000)* so you don't get bogged down in trivial arithmetic.
> * **Verify assumptions:** Explicitly verify your core assumptions with the interviewer after stating them *(e.g., "I'm assuming 50M DAU and a 90:10 text-to-image ratio. Does that sound reasonable for this scope?")*.
