# System Design (HLD) Lecture 5: Horizontal vs Vertical Scaling

---

## 1. What is Scaling?

* **Main Idea:** Taking a system built for **10 users** on 1 laptop and expanding it to handle **10 Crore users**.
* **Analogy (Room vs. Apartment):** 
  * 1 room fits 3–4 people.
  * To house 1,000 people, you build an apartment (a collection of rooms).
* **Key Interview Point:** First question in scaling interviews: *"Will you do vertical or horizontal scaling, and why?"* There is no single "always right" answer—it strictly depends on the use case.

## 2. Vertical vs. Horizontal Scaling

### The Weight-Lifting Analogy

A kid can lift **20 kg**, and you need **40 kg** lifted:

* **Vertical Scaling:** Send the same kid to the gym to build muscle/height $\rightarrow$ lifts 40 kg (up to a human limit, say 200 kg max).
* **Horizontal Scaling:** Bring another similar kid to stand side-by-side $\rightarrow$ together they lift 40 kg. Need more? Line up 3–4 more kids.

### Side-by-Side Comparison

| Factor | Vertical Scaling | Horizontal Scaling |
| :--- | :--- | :--- |
| **What you do** | Buy a bigger server (more CPU, RAM, disk). | Buy more identical servers (2, 3, 10, 10,000 machines). |
| **Complexity & Code** | **Simple.** Zero code changes—just ask AWS to upgrade. | **Complex.** Needs a Load Balancer, stateless servers, and possible code changes. |
| **Cost** | Grows **exponentially** as hardware gets bigger. | Grows **linearly** (1 kid = ₹10 $\rightarrow$ 2 kids = ₹20). |
| **Hardware Ceiling** | **Strict limit** (e.g., max 1 TB RAM available in the world). | **Practically unlimited** (keep adding machines). |
| **Downtime** | **Yes.** AWS stops app on old server, copies code to new server, and restarts (site goes down briefly). | **Zero downtime.** Add a 5th machine seamlessly while 4 machines keep serving users. |

---

## 3. Trade-offs: When to Use What?

* **Early Stage / Startups:** Start with **Vertical Scaling** when load doubles or triples because it's simple and avoids unnecessary complexity.
* **Growing Scale:** Once vertical cost spikes exponentially or hits the hardware ceiling $\rightarrow$ move to **Horizontal Scaling**.
* **Big Companies:** Use a hybrid approach (**Vertical first, then Horizontal**) $\rightarrow$ build powerful vertically scaled machines, then place many of those big machines side-by-side horizontally.
* **Database Scaling:**
  * Prefer **Vertical Scaling** for databases as long as possible.
  * Horizontal scaling a DB means splitting/sharding user records across machines (e.g., 10 users split as 3 on DB1, 4 on DB2, 3 on DB3), which is super complex.
  * Only switch to DB sharding when vertical scaling becomes impossible or absurdly expensive (e.g., AWS asks for ₹1 Crore).

## 4. Horizontal Scaling Architecture: Stateful vs. Stateless Servers

### Why Load Balancers Enter the Picture

In horizontal scaling, independent servers (`C1`, `C2`, `C3`) run the exact same app code. Users don't connect directly to `C1`, `C2`, or `C3`—they only talk to a **Load Balancer (LB)** in front, which distributes requests so one server doesn't choke while others sit idle.

```
[ User 1 / User 2 / User 3 ] 
             │
             ▼
     [ Load Balancer ] (Main Gate)
       ┌─────┼─────┐
       ▼     ▼     ▼
     [C1]  [C2]  [C3]  (Servers)
```
*Basic request routing in a horizontally scaled system using a Load Balancer.*

---

### The Problem: Stateful Servers

* **What "State" Means:** Any info about a user or their ongoing session (user ID, login status, cart items).
* **Amazon Shopping Example:**
  1. Pratyush creates an account $\rightarrow$ LB sends request to `C1`. `C1` saves username/password locally. `C2` and `C3` know nothing.
  2. Pratyush adds a Dell laptop to cart $\rightarrow$ Request goes to `C1`. `C1` saves cart info in its RAM.
  3. Pratyush clicks Pay **₹65,000** $\rightarrow$ LB routes request to `C2`. `C2` rejects it because `C2` has no idea who Pratyush is or what's in his cart.
* **Hotel Analogy:** Ordering and eating food at Ram Hotel, then walking into Shyam Hotel to pay **₹720** $\rightarrow$ Shyam Hotel rejects you.
* **Why Sticky Routing (always sending Pratyush to `C1`) Fails:** Creates uneven load (`C1` has a huge queue while `C2` & `C3` sit empty), and if `C1` crashes, Pratyush loses his session and has to log in again.

---

### How Login, Sessions & Cookies Work

1. **Authentication:** User logs into Instagram with username/password $\rightarrow$ Server verifies and creates a **Session ID** (e.g., `abx...`, valid for 2, 7, or 10 days—like a security guard remembering your face after registration).
2. **Cookie Storage:** Server sends this Session ID to the browser (Chrome), stored as a **Cookie**.
3. **Subsequent Visits:** On future visits, the browser automatically sends the Cookie $\rightarrow$ Server reads it and keeps the user logged in without asking for credentials again.

---

### The Fix: Stateless Servers

* Stop storing cookies, session IDs, or cart state inside `C1`, `C2`, or `C3`'s local memory/disk.
* Move all session/cart data into a **Shared Store / Central System** accessible by every server.
* Now any server (`C1`, `C2`, or `C3`) checks the shared store, sees Pratyush's cart, and completes the ₹65,000 payment (like connected hotels checking a central ledger to accept your ₹720 bill).

```
[ User (with Cookie) ]
          │
          ▼
  [ Load Balancer ]
    ┌─────┼─────┐
    ▼     ▼     ▼
  [C1]  [C2]  [C3]  (App Servers)
    └─────┬─────┘
          ▲
          │ (Read / Write State)
          ▼
[ Shared State Store ] (Sessions / Cart)
```
*Stateless architecture where any server can handle any user request by reading/writing state to a shared store.*

## 5. The 4 Jobs of a Load Balancer

1. **Spread Traffic:** Distribute incoming user requests evenly/smartly across servers.
2. **Health Check (Heartbeat):** Ping servers every **5 or 10 seconds** ("Are you okay?"). If a server fails to respond (e.g., **3 consecutive misses**), LB marks it dead and stops sending traffic to it.
3. **Add / Remove Machines:** Seamlessly attach new servers (e.g., `C4`) or remove existing ones without downtime.
4. **Security:** Acts as the society's **Main Gate** (Public IP) shielding backend servers `C1`, `C2`, `C3` (Private IPs / house addresses). Users only know the LB's IP and cannot directly reach or attack backend servers.

## 6. Load Balancing Algorithms

| Algorithm | How It Works | Pros / Cons & Examples |
| :--- | :--- | :--- |
| **1. Round Robin** | Sends requests sequentially like dealing playing cards:<br>`Req 1` $\rightarrow$ `C1`<br>`Req 2` $\rightarrow$ `C2`<br>`Req 3` $\rightarrow$ `C3`<br>`Req 4` $\rightarrow$ `C1` | • **Pro:** Simplest, zero overhead.<br>• **Con:** Ignores request weight & server load. Can overload `C1` (at 99% load) with heavy requests (payments, generating a game) while `C2` sits at 40%. |
| **2. Load-Based** | Routes each new request to whichever server currently has the lowest load / most free capacity. | • **Fixes Round Robin overload.**<br>• *Analogy:* 3 cooks (making tea, paratha, 7-course meal) $\rightarrow$ give next order to the tea cook who finishes fastest. |
| **3. Weighted Round Robin** | Assigns weights based on hardware capacity.<br>E.g., `C1` (8 GB RAM) = weight 1, `C2` (128 GB) = weight 2, `C3` (1 TB) = weight 3 (total = 6). | • Out of every **6 requests**: 1 goes to `C1`, 2 to `C2`, 3 to `C3`, then repeats.<br>• Best when servers aren't identical. |
| **4. Hash-Based / Rule-Based** | Converts info (User ID, IP, Port) into a number via hashing (e.g., `17 % 10 = 7`, `27 % 10 = 7`, `13 % 10 = 3`) **OR** routes by request type. | • Pre-determined routing regardless of load.<br>• *Rule Example:* Video requests $\rightarrow$ `C1`, Payment requests $\rightarrow$ `C2`, Orders $\rightarrow$ `C3`. |

## 7. Must Remember for Interview (From Video)

1. **Scaling Definition:** Scaling means expanding a system from a handful of users (10) to massive scale (10 Crore users).
2. **Vertical vs. Horizontal:** Vertical scaling upgrades a single machine (bigger CPU/RAM/disk); Horizontal scaling adds multiple machines side-by-side.
3. **Vertical Trade-offs:** Zero code changes, exponential cost, a strict hardware ceiling, and brief downtime during migration.
4. **Horizontal Trade-offs:** Linear cost, practically unlimited ceiling, and zero downtime when adding nodes, but adds architectural complexity.
5. **Strategy:** Start with Vertical scaling in early stages; switch to Horizontal scaling when cost spikes or hardware limits are hit (big companies combine both).
6. **Databases:** Prefer Vertical scaling for Databases as long as possible because horizontal DB sharding is very complex.
7. **Stateless Requirement:** Horizontal scaling requires **Stateless Servers**—user sessions/cookies/cart state must live in a shared store, not on individual app servers.
8. **Session Cookies:** Cookies store a server-generated Session ID in the browser so users don't have to log in on every request.
9. **Load Balancer Roles:** Performs 4 jobs: traffic distribution, health checks (heartbeats), adding/removing servers, and security (hiding private server IPs behind a public gate).
10. **Routing Algorithms:** Know the 4 LB algorithms: Round Robin, Load-Based, Weighted Round Robin (for unequal server specs), and Hash/Rule-Based.

## 8. Quick Revision Table

| Concept | One-Line Summary |
| :--- | :--- |
| **Vertical Scaling** | Upgrading a single server's hardware (CPU/RAM/disk); simple but hits exponential cost and hardware ceilings. |
| **Horizontal Scaling** | Adding multiple servers side-by-side; scales linearly with zero downtime but requires a Load Balancer. |
| **Stateful vs. Stateless Server** | Stateful keeps user data locally on one server; Stateless stores session data in a shared store so any server can serve any request. |
| **Cookie & Session ID** | Server issues a temporary Session ID stored as a browser cookie to keep users authenticated across requests. |
| **Heartbeat (Health Check)** | Periodic ping from Load Balancer to servers to detect dead machines and stop routing traffic to them. |
| **Round Robin** | Distributing requests sequentially one-by-one across servers without checking current load. |
| **Load-Based Routing** | Sending incoming requests to the server with the least current workload. |
| **Weighted Round Robin** | Distributing requests proportionally based on server hardware capacity weights (e.g., 1:2:3). |
| **Hash-Based Routing** | Mapping user attributes (ID/IP) or request types deterministically to specific servers. |
